# Test Prep Platform

Next.js App Router and Payload CMS foundation for the test-prep platform PRD. The public frontend currently runs on clearly labeled mock data while client approval for backend work is pending. Payload schemas and admin setup remain in the repository, but the demo public routes do not query Payload or require PostgreSQL.

## Local setup

Requirements for the public demo: Node.js 20.18.1 or newer and npm 10 or newer. PostgreSQL and Docker Compose are only needed to run the Payload admin.

To preview the mock frontend, install packages with `npm install`, run `npm run dev`, and open `http://localhost:3000`. The demo includes `/demo-tests`, `/sample-aptitude-practice-test`, and `/courses/sample-aptitude`.

To run Payload Admin locally:

1. Copy the sample environment file with cp .env.example .env.
2. Replace PAYLOAD_SECRET with a unique value of at least 32 characters. For example, generate one with openssl rand -base64 48.
3. Set ADMIN_EMAIL, ADMIN_PASSWORD, and ADMIN_NAME in .env for the one-time administrator bootstrap.
4. Start the local database with docker compose up -d postgres.
5. Install packages with npm install if you have not already.
6. Create the first administrator with npm run cms:create-admin.
7. Start Next.js with npm run dev and open http://localhost:3000/admin.

To load CMS content for a team demo, run `npm run cms:seed-demo` after PostgreSQL is running. It creates or refreshes clearly labeled demo records as drafts in the local database. The command only accepts a local database URL, is safe to rerun, and does not create active products or publish content. Set `ADMIN_EMAIL`, `ADMIN_PASSWORD`, and `ADMIN_NAME` in `.env` before the admin bootstrap; do not use real credentials in the demo environment.

The PostgreSQL credentials in the Compose file are for local development only. Use managed PostgreSQL credentials in hosted environments. Never commit .env.

## Project structure

    src/
      access/       Shared Payload role and publishing rules
      app/
        (frontend)/ Public mock routes and design tokens
        (simulation)/ Full-screen runner layout without public navigation
        (payload)/  Payload admin and API routes
      blocks/       Reusable CMS page-content block schemas
      collections/ Payload collection schemas, one domain per file
      fields/       Reusable Payload field definitions
      lib/          Runtime configuration and shared server utilities
      mocks/        Clearly labeled frontend demo data
      payload.config.ts
      payload-types.ts  Generated by Payload; do not edit manually

As product components are added, put domain-specific code in src/features/<domain>. Keep route files thin. Put genuinely reusable presentational components in src/components; avoid a generic component library before real product needs establish its API.

## Content and access rules

- Tests, categories, test variants, test change entries, pages, FAQs, courses, modules, lessons, questions, quiz configurations, and products are modeled as separate collections.
- Editorial content uses Payload drafts and versions plus an explicit review status.
- The public demo uses `src/mocks/testPrepData.ts`; the category, practice guide, and course outline are marked as demo content and noindex.
- The Payload team-demo seed command (`npm run cms:seed-demo`) creates draft-only sample catalog, course, page, FAQ, question, and quiz-config records in local PostgreSQL.
- When backend work is approved, public loaders must return only approved and published records.
- Questions and quiz configurations stay private to staff APIs. Never expose answer keys in public page data or static bundles. Learner quiz endpoints must return a deliberately sanitized question shape and score answers on the server.
- Course records hold the Free Starter content selection and duration; products hold the configured one-time price and access duration.
- Page blocks are defined as Payload schemas. The mock public pages and presentational components are in place; import validation and learner delivery APIs remain for approved backend work.
- Payload Local API calls skip access checks by default. For user-context operations, pass the authenticated user and set overrideAccess to false; privileged server calls must be narrow and intentional.
- After changing collection schemas, regenerate Payload types with npm run payload:types.
- Local development syncs the schema automatically. Before production deployment, create and review a migration with npm run payload:migrate:create and apply committed migrations with npm run payload:migrate.

## Useful commands

- npm run dev — local development
- npm run lint — ESLint
- npm run typecheck — TypeScript
- npm run format — format files with Prettier
- npm run format:check — check formatting
- npm run payload:types — regenerate Payload TypeScript types
- npm run payload:importmap — regenerate the Payload admin import map
- npm run payload:migrate:create — generate a database migration after a schema change
- npm run payload:migrate — apply committed migrations in a deployment environment
- npm run test:int and npm run test:e2e — test suites configured for later feature work

## Design foundation

The frontend starts with neutral color, spacing, typography, radius, and focus tokens in src/app/(frontend)/styles.css. This is a foundation only; it is not a finished product design. Prefer semantic tokens and accessible focus states when building components.

## Deployment notes

Payload needs a persistent PostgreSQL database and permanent media storage in production. Local disk uploads are only for local development. Connect an S3-compatible provider (such as S3 or R2) before production uploads are enabled.
